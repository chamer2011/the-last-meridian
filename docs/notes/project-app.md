# project-app

*The game (Almagest Explorer's, The Last Meridian until 2026-11-08) as an installed Windows app (Electron), built 2026-11-01. How game changes reach it, and what that means for restarting and testing*

The player asked for a real app, just for themselves, so they pay nothing for signing or Steam. `app/main.js`, `app/choices.js`, `app/build.js` and `app/icon.ico` in the game folder, with the installer at `dist/The-Last-Meridian-Setup.exe`. It's installed for the player with shortcuts on the desktop and in the Start menu. `backups/before-app-2026-11-01` has the version before it.

Renamed with the game on 2026-11-08: the window and `productName` are Almagest Explorer's, the exe is `Almagest Explorers.exe` (`executableName`, no apostrophe in a file name), the installer `dist/Almagest-Explorers-Setup.exe`, the shortcut Almagest Explorer's. The app id `com.lastmeridian.game` was kept on purpose, so a new installer replaces the old app instead of sitting beside it. Electron names the settings folder after the app, so it's `%APPDATA%\Almagest Explorer's` now; `takeOverOldFiles` in `app/main.js` (`oldFilesToTakeOver` in `app/choices.js`) copies `%APPDATA%\The Last Meridian` across the first time the new name runs with nothing of its own, saves and key included for anyone without the game's folder, and `looksLikeTheGame` accepts the page under either title. The owner's installed app keeps the old name until they run a new installer, which I don't run for them; its window shows the new page title anyway. For release 0.6.0 the build was given a first run of its own (33 checks), with the takeover skipped when `--user-data-dir` is given, so a test run on this computer takes nothing over from the installed app's folder; the owner's own installer was rebuilt at 0.6.0, and they haven't run it.

Decisions that aren't obvious from the code:
- On this computer the installed app imports `D:\Test IA\server.js`, not its own copy, and the saves stay in `D:\Test IA\data`. So a change to the game reaches the app the next time it's closed and reopened, with no rebuild. Only a change in `app/` needs `npm run build-app` and running the installer. Its own copy is only for a computer without the folder, where it keeps saves in `%APPDATA%\The Last Meridian\data`.
- Port 3210 is the lock: only one server can hold it, and two would overwrite each other's autosave. The app joins a game that's already running there, and takes over if that game stops. `node server.js` exits with "already running" if the app has the port.
- Closing the window during an AI turn hides it and quits after the turn is saved, because a browser tab closing never lost a turn. A pending walk is saved on quit.

**Why:** the player has no coding experience and shouldn't have to reinstall anything when a session changes the game.

**How to apply:** "restart the game" now means asking the player to close and reopen the app. If they have it open, starting the `start` preview does nothing useful, because the server exits and the page shows the app's running copy, with the old code. Test with `GAME_DATA_DIR` and `PORT` as before: the app honors both, plus `--user-data-dir`. In an Electron ESM main file, `await app.whenReady()` at the top level never finishes, because ready waits for the file. The player sometimes plays in this session's Browser pane instead, through the `start` preview, so check `preview_list` and whether the app's running before saying how to restart: if it's the preview, restart that once nothing's busy, and they press Continue. While they play, the autosave changes and a moving mouse keeps the clock awake, so "your real save wasn't touched" and the two-minute check in my window tests can fail for that reason alone. Related: [project-last-meridian](project-last-meridian.md), [project-walk-around](project-walk-around.md).

## A second copy beside it (2026-11-16)

At their "Could you make this an desktop application", about a copy of the game they'd downloaded from GitHub and unzipped on the desktop (`C:\Users\jsvp2\Desktop\the-last-meridian-main`, GitHub's main at 0ccb6ea, exactly), the game gained a second app. They'd opened the first app at 17:16 that day (it started fine), closed it at 17:18, unzipped the download at 17:20 and asked; while I worked, a game was started in the download with its `start-game.bat` (a captain called Sana Vey, autosave at 17:27). Every build of the app on this computer would have played `D:\Test IA` all the same, because the first app's settings remember that folder and a new build with the same name shares them, and it would have joined a game already on port 3210; so the copy is an app of its own.

`node app/build.js --copy` (`COPY_APP` and `installerSettings` in `app/choices.js`, `appIdentity` read by `app/main.js` from the `gameCopy` flag in the package.json built into it) makes **Almagest Explorer's (copy)**: package name `almagest-explorers-copy` (a per-user install goes in a folder named after the package), id `com.lastmeridian.game.copy` (the uninstall entry and the taskbar), exe `Almagest Explorers Copy.exe`, installer `dist/copy/Almagest-Explorers-Copy-Setup.exe`, a shortcut of the app's name, settings in `%APPDATA%\Almagest Explorer's (copy)`, port 3220. It remembers the folder it was built in, like the owner's own installer, so it plays that folder's game and saves; with `--for-others` too, the game inside it. A copy never takes over the old name's files (`oldFilesToTakeOver` with `copy`), because they'd send it to `D:\Test IA`. The bought art never goes in an installer: `--licensed=<folder>` bakes where it is, and the app sets `GAME_LICENSED_DIR` to it when the folder it plays has no `licensed/` of its own.

The one in use was built in the Desktop folder with `--licensed="D:\Test IA\licensed"` and installed for them with the installer's `/S`, since it can't replace the first app. A risk left: the port is the lock for one folder only, so that folder's `start-game.bat` (port 3210) and the copy (3220) open at once would both save into the Desktop folder; the README says not to.

The built copy and then the installed one each passed a first run of 16 checks (`first-run.mjs`, scratch: port 3297 and a throwaway save folder, a new game made and Continued to the bridge, the bought art served, the copy's own settings remembering the Desktop folder, no errors on the page, and the first app's settings and exe, the Desktop folder's autosave and this folder's untouched). Opened from a script, its window can open behind others, and Windows then slows a covered window's drawing: the ship once sat at 0% on its loading screen, and once took 40 s, where 2 to 3 s is usual brought to the front. Opened from its icon, it comes up in front.

Found on the way and left alone: Windows' list of installed apps still names the first app The Last Meridian 0.1.0, with an uninstaller in `%LOCALAPPDATA%\Programs\last-meridian`, which is gone; the install of 0.6.0 on 2026-11-08 went to `%LOCALAPPDATA%\Programs\almagest-explorers` and left that entry as it was. Uninstalling the first app from that list would fail; its own `Uninstall Almagest Explorers.exe` is in its folder, and a new installer of the first app would write the entry afresh.
